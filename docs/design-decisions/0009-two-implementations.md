# 0009. Two implementations: `purejl` the oracle, `backend-jl` the optimizer consumer

- Status: Accepted
- Date: 2026-07-31

## Context

Gate B4 — running the compiler's own `tests/purs/passing` corpus — left Jurist
at 341/347, with a residue that is **not** a list of small independent defects.
Four of the six causes are shared with Pythia and Gnomon, and the largest is
**TCO**: [0003](0003-tco-trampoline.md)'s dispatch loop handles self-recursion,
and mutual and partial tail calls escape it (`TCOMutRec`, `PartialTCO`, `3957`).

Reading the mature non-JS backends produced an inversion worth restating here,
because it changes what "prior art" means for this repo. purerl,
`purescript-lua`, purescm and `backend-wasm` all target runtimes with **native
proper tail calls**, so none of them ever solved this — `grep -rn trampolin`
finds nothing in purerl or `purescript-lua`. Julia gives no TCO guarantee
([0003](0003-tco-trampoline.md)), which leaves **JavaScript** as the only
comparable case, and `purescript-backend-optimizer` has solved it in
`Codegen/Tco.purs`: a `TcoRole { joins, isLoop }` analysis that collapses a
mutually-recursive group into a single loop with join-point dispatch.

The alternative was hand-porting that analysis into three separate Haskell
generators. `TCOMutRec` also asserts the ES backend's exact TCO **frontier** —
it requires that certain shapes *do* overflow — so three hand-ports would be
three chances to drift from a boundary the corpus checks byte-for-byte.

## Decision

Add a **second implementation** in this repo: `backend-jl/`, a PureScript
program consuming `purescript-backend-optimizer`'s `BackendSyntax`/`NeutralExpr`
IR and lowering it to Julia. It is **additive**. `purejl` (Haskell, raw CoreFn)
stays, and stays the correctness **oracle**.

This mirrors Gnomon's ADR-0007 and Pythia's ADR-0003, and extends the family
decision recorded in
`docs/kb/architecture/adopt-backend-optimizer-family-wide.md` (the `docs` repo).

Three properties make it worth having two:

**1. The oracle is the honesty layer.** A single implementation cannot check
itself. Running both lanes over the same corpus and diffing them is what makes
"conformant" a checkable claim rather than a hope — the same argument
[0004](0004-differential-conformance.md) makes for JS-vs-Julia, applied to
Julia-vs-Julia.

**2. One runtime, shared, not forked.** `backend-jl` emits one Julia module per
PureScript module using `purejl`'s own naming, so `purejl_runtime.jl` and every
`<Module>_foreign.jl` are produced by `purejl` and consumed unmodified. Neither
is generated by `backend-jl` and neither is checked in beneath it, and
`bin/conformance.sh` fails if one ever appears. This is a direct response to
evidence: Gnomon kept two ~2,400-line Go runtimes, they silently diverged by two
symbols, and it took a red CI and a symbol-set diff to notice (2026-07-31). Here
the divergence is not merely discouraged, it is structurally unavailable.

**3. Expression-oriented emission**, which is where the port parts company with
`backend-py` — see Consequences.

## Consequences

**Measured on the shared differential corpus, 2026-07-31: 20/20 green**
(17 byte-identical to the JavaScript reference, 3 ledger-only) —
`backend-jl/run_conformance.sh`, first full run.

**Measured on `tests/purs/passing` @ v0.15.15, both lanes run the same day with
the same harness** (`purs-corpus/run_corpus.py`):

```
purejl      341/347 = 98.3%     (the oracle)
backend-jl  342/347 = 98.6%     (this lane)
```

Every test on which the two differ:

| test | `purejl` (oracle) | `backend-jl` (optimizer) | why |
|---|---|---|---|
| `3957` | ✗ `StackOverflowError` | **PASS** | TCO |
| `PartialTCO` | ✗ `StackOverflowError` | **PASS** | TCO |
| `StringEscapes` | ✗ `BUILD_ERR` | **PASS** | string literals |
| `NegativeIntInRange` | PASS | ✗ `CODEGEN_ERR` | upstream decoder |
| `StringEdgeCases` | PASS | ✗ `CODEGEN_ERR` | upstream decoder |
| `2136` | ✗ | ✗ | `Int` wrapping |
| `TCOCase` | ✗ timeout | ✗ timeout | ADT representation (below) |
| `TCOMutRec` | ✗ | ✗ | join points |

Three fixed, two regressed, three shared: 341 + 3 − 2 = 342. The regressions are
stated plainly because they are the price of the lane, and both are **upstream
in `purescript-backend-optimizer`'s CoreFn JSON decoder**, not in this lowering
— the same two the Python lane hit, which is itself corroboration that they are
the decoder's and not either backend's:

- `NegativeIntInRange` is `n = -2147483648`. `purs` emits that as
  `Data.Ring.negate` applied to `IntLiteral 2147483648` — verified by reading
  the CoreFn — and `decodeInt` rejects the literal because `Int.fromNumber` sees
  it outside the `Int32` range. The literal really is out of range; the
  *expression* is not, which is the whole point of the test's name.
- `StringEdgeCases` carries a lone surrogate, which `purs` emits as an array of
  code units. `decodeStringLiteral` handles that form; some other field on the
  path is decoded with plain `decodeString`, which does not.

`2136` is untouched and always will be: `Int` wrapping is a *representation*
decision in the lowering, not an IR decision. It needs the Gate C9 answer, and
the same answer on all three backends.

`BigFunction` — which defeats the Python oracle outright, and which motivated
Pythia's whole lambda-lifting pass — passes on **both** Julia lanes and always
did. Julia has no analogue of CPython's ~200-deep parenthesis cap, so the wall
that shaped the Python backend simply is not there.

### Expression-oriented, and why that is the whole story

`backend-py` is statement-oriented, and had to be: Python's `lambda` takes an
expression, so blocks can only be encoded as `(lambda: ((x := e), body)[-1])()`.
It paid for that choice — **an IR scope stopped being a target scope**, and four
separate name-collision classes followed (sibling `Let`s at the same de Bruijn
level; top-level bindings sharing module scope; loop dispatchers sharing module
scope; generated names colliding with user identifiers). Three of the four were
found by a failing corpus test rather than by inspection, and closing them took
a module-wide rename pass.

Julia has no such tension. `let x = v; body end` and `if c; a; else; b; end` are
**both scoped blocks and expressions**. So a `Let` is a `let`, a `Branch` is an
`if`/`elseif` chain, and every IR scope is a real Julia scope — the property
`backend-go` buys with an IIFE per binding, here for free and without the
closure. There is no statement buffer, no lambda lifting, no rename pass, and no
locals map; the optimizer's within-a-scope uniqueness of de Bruijn levels is
exactly the guarantee the target needs.

**The prediction that this would be the easier port was right, and it is worth
recording *why*, because it is not "Julia is nicer".** It is one specific
language property — scoped blocks that are also expressions — and it is the same
property that decides how hard this port is for any future target.

The saving does **not** show up as line count: `backend-jl` is 1,323 lines
against `backend-py`'s 1,332, near enough identical, and against `purejl`'s
1,935 (999 of which is the generator proper, the rest the foreign-shim
catalogue this lane does not duplicate). It shows up as *what is not there* —
no statement buffer, no lambda-lifting pass, no rename pass, no locals map —
and as the fact that the lane compiled and went 20/20 on its first full run,
with none of the four Python hazards appearing at any point. Cost is roughly
constant across a port; correctness risk is not.

The one place statements are unavoidable is a TCO loop body, which has to
`return` a continue/stop signal. That walk is the only statement-mode code in
the emitter, and it uses `let` for its bindings so the scoping guarantee holds
there too.

### Mutual tail recursion, which goes past the oracle

[0003](0003-tco-trampoline.md) deliberately did not trampoline mutual recursion.
This lane does, for the *direct* case: a recursive group of more than one member
gets a leading branch register and the members share one dispatch loop, so a
tail call to a sibling is `return (1, (idx, …))` like any other. It needed **no
runtime change** — the `while` is the runtime, and it is the same shape
[0003](0003-tco-trampoline.md) already chose, for the same reason
(function-call-per-iteration, so a closure built in the body cannot capture the
last iteration's bindings).

`3957` and `PartialTCO` are what that buys.

### Two frontiers this measurement names precisely

**Join points.** ~~`TCOMutRec` still fails, with `StackOverflowError`.~~ Its
`tco1` defines `g` in a `where` *inside* `f`, so the optimizer marks each a
separate self-loop and the cross-calls between them stay ordinary stack calls.
The optimizer already computes what is needed — `TcoRole.joins` — and this lane
reads only `isLoop`. The shape that fits is already built: a join point is a
local binding all of whose calls are tail calls from inside the loop, so it can
become **another member of the same dispatch group** — one more index in the
branch register. The mutual-recursion machinery is the join machinery.

It should **not** copy backend-es's lowering, where a join point assigns the
enclosing loop's registers and returns, and the caller then `continue`s. That
works because JavaScript's loop variables are mutable state in an enclosing
closure. Here the registers are the dispatch function's *parameters*, precisely
so each iteration gets its own bindings, so nothing can reach in and assign them.

> **Progress (2026-07-31): implemented, on this lane and on `backend-py`.**
> The sketch above was right about the shape and incomplete about the cost. A
> join point does become another branch — but folding it in means *lifting it out
> of the member it was written inside*, and it may have captured variables from
> there. `tco4`'s `g y' = f (x + 2) y'` reads `f`'s parameter `x`; a jump leaves
> the frame, so `x` has to travel too.
>
> The fix is one idea: **make the register file keyed by LOCAL rather than by
> position** — one slot per distinct local any branch binds, being every member's
> parameters plus the free variables the join points captured. `x` then gets one
> slot whether it arrives as `f`'s parameter or as `g`'s capture. Every branch
> binds every slot on entry, which costs a few dead assignments and buys the
> invariant the whole thing rests on: at any jump site every slot is in scope, so
> a captured variable survives an arbitrary chain of jumps.
>
> Free variables are filtered by de Bruijn level against the group's own
> parameters. Anything bound further out is already reachable by ordinary lexical
> capture — the dispatch function is emitted *inside* the enclosing scope — and
> putting it in a register would shadow it. `tco3`'s `g` reads `y0` and `j` from
> two scopes up and must not.
>
> Measured on `TCOMutRec`'s four positive cases, against the JavaScript reference
> at depth 100,000 (byte-identical), and then at **10,000,000** to show the stack
> is flat rather than merely deep:
>
> ```
> tco1 20000000   tco2 20000000   tco3 24999997   tco4 20000000
> ```
>
> `tco3` is the one that makes the design earn its keep: its `g` is *both* a
> self-loop and a join, so it needs to be a branch that can jump to itself and to
> `f`.
>
> **`TCOMutRec` as a whole still fails, and now for a reason that is not ours.**
> The test also asserts that four *non*-TCO-able shapes MUST overflow
> (`assertThrows \_ -> ntco2 100000`), and the optimizer inlines `ntco2`'s and
> `ntco4`'s helper away, turning each into a plain self-tail-loop that completes.
> The generated Julia for `ntco2` contains no join machinery at all — one branch,
> no branch register — so this is not the join work: it is
> `purescript-backend-optimizer`'s inliner moving a frontier the test pins down.
> Confirmed independently on `backend-py`, a different lowering over the same
> optimizer, which also completes `ntco2`, while `purepy` (the oracle, no
> optimizer) overflows exactly as the test demands.
>
> That puts `TCOMutRec` where Gnomon's half of it already sits: the
> `assertThrows` assertions describe a *runtime and optimizer* property rather
> than PureScript semantics, and belong in the divergence ledger next to `INT64`
> and `ASTRAL`. The corpus now reports it as `Assertion failed: An error should
> have been thrown` rather than a stack overflow, which is the failure saying so
> itself.

**`TCOCase`, and what it says about [0001](0001-runtime-representation.md).**
Both lanes time out at 180 s, so it is not this lane's doing — but it is worth
characterising, because the cause is the ADT representation and not the code
generator. `TCOCase` builds a 10,000-deep `data Data = One | More Data` and then
walks it. Timing the generated program at reduced depths:

| depth | 20 | 50 | 100 | 200 | 400 |
|---|---|---|---|---|---|
| wall | 0.5 s | 1.0 s | 2.7 s | 11.2 s | 51.2 s |

That is roughly 4.5× per doubling of depth — superlinear by a wide margin, and
10,000 is nowhere near reachable. The structural reason is that Julia tuples are
**concretely typed**, so `("More", x)` at depth *d* has a type nested *d* deep:
`typeof` renders as 1,513 / 3,013 / 6,013 characters at depth 100 / 200 / 400,
i.e. the type's *size* is linear in the value's depth. A hand-written build-and-
walk of the same shape in plain Julia is much cheaper than the generated program,
so the depth-growing type is necessary but not sufficient to explain the whole
factor; the remainder is uncharacterised and is not claimed here.

[0001](0001-runtime-representation.md)'s "Alternatives considered" rejected
struct/`@enum` ADTs for v1 and said to *"revisit if it ever bounds
performance."* This is that moment, and it is now recorded there.

### Costs

**Two toolchains in one repo.** Haskell/stack for `purejl`, PureScript/spago for
`backend-jl`. Pythia and Gnomon already live with this.

**A moving upstream dependency**, pinned through the package set.

## Alternatives considered

**Replace `purejl` with `backend-jl`.** Rejected: it discards the oracle, and
with it the only mechanism that can catch a codegen bug neither author thought
to test. Two lanes that must agree is the whole method
([0004](0004-differential-conformance.md)).

**Hand-port `Codegen/Tco.purs` into `purejl` (Haskell).** Rejected as the
family-wide answer: three ports of one analysis, each free to drift from a
frontier the corpus asserts byte-for-byte. It remains available for `purejl`
alone if the oracle ever needs to close the same gap.

**Fork the runtime into `backend-jl/`,** as Gnomon did. Rejected on measured
evidence — see Decision, point 2. Three helpers (`_int32`, `_zshr`, `_int_div`)
were instead added to the *shared* runtime, holding exactly the semantics
`Data_Int_Bits_foreign` and `Data_EuclideanRing_foreign` already hold for the
oracle. One definition each, both lanes.

**Port `backend-py`'s statement-oriented emitter.** Rejected: it would have
imported four hazard classes and a rename pass to solve a problem Julia does not
have. Statements are what an expression-only lambda forces; they are not the
better shape when the target has scoped block expressions.
